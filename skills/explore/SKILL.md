## 一、技能概述

需求探索是整个研发流程的起点。目标是在开始正式需求文档之前，充分理解用户的真实意图，识别项目类型和核心约束，收集足够的上下文信息，为后续 PRD 撰写提供可靠基础。

**核心原则：**
- 不假设、不猜测：信息不足时主动提问
- 结构化输出：所有信息按固定格式整理
- 可追溯：每条需求都能追溯到用户原始描述

## 二、执行步骤

### 步骤 1：理解用户意图

仔细阅读用户的原始需求描述，提取以下关键信息：

- 用户想要什么（目标）
- 用户为什么要（动机）
- 用户谁来用（受众）
- 用户什么时候要（时间约束）

将原始描述原文记录到需求摘要的「原始需求」字段中，不做任何改写。

### 步骤 2：识别项目类型

根据需求描述判断项目类型，支持以下类型：

| 项目类型 | 识别关键词 | 典型场景 |
|---------|-----------|---------|
| Web 网站 | 官网、网站、网页、落地页 | 企业官网、营销页、产品展示 |
| Web 应用 | 系统、平台、后台、管理 | 后台管理系统、SaaS 平台 |
| API 服务 | 接口、API、微服务、后端 | RESTful API、GraphQL 服务 |
| 小程序/H5 | 小程序、微信、H5、移动端 | 微信小程序、移动 H5 应用 |
| 数据脚本 | 脚本、自动化、数据、报表 | 数据处理、定时任务、ETL |
| 移动应用 | App、iOS、Android、Flutter | 原生/跨平台移动应用 |
| 桌面应用 | 桌面、Electron、客户端 | 桌面工具、跨平台客户端 |
| 基础设施 | 部署、CI/CD、Docker、K8s | DevOps、基础设施即代码 |
| 微服务架构 | 微服务、服务网格、gRPC、分布式 | 微服务后端系统、分布式应用 |
| Monorepo | monorepo、turbo、nx、lerna | 前后端统一仓库、多包管理 |
| 库/SDK | 库、SDK、组件库、工具包 | 内部组件库、开源 SDK |
| CLI 工具 | 命令行、CLI、脚手架、工具 | 开发工具链、自动化脚本 |

如果无法确定类型，向用户展示类型列表让其选择。

### 步骤 3：收集关键信息

如果用户描述中缺少以下关键信息，主动提问补充。提问遵循「最少轮次」原则：一次性列出所有需要确认的问题，避免反复打扰用户。

**必须收集的信息：**

1. **项目目标**：这个项目要解决什么问题？核心价值是什么？
2. **目标用户**：谁会使用这个产品？（C 端用户 / B 端员工 / 内部团队）
3. **核心功能**：列出必须实现的功能（区分「必须有」和「最好有」）
4. **参考案例**：有没有类似的网站或产品可以参考？
5. **技术约束**：有没有指定的技术栈、部署环境、兼容性要求？
6. **时间要求**：期望什么时候交付？有没有硬性截止日期？
7. **预算范围**：大致预算区间（影响技术选型和功能范围）
8. **安全要求**：是否涉及用户隐私数据？是否需要等保认证？数据加密要求？
9. **合规要求**：是否有行业合规要求（金融、医疗、教育等）？

**按项目类型的补充问题：**

- Web 网站：需要响应式设计吗？需要 SEO 吗？有品牌色/Logo 吗？
- Web 应用：需要用户认证吗？需要权限管理吗？数据量预估多少？
- API 服务：预计 QPS 多少？需要鉴权吗？有哪些上下游系统？
- 小程序：需要微信支付吗？需要登录授权吗？
- 数据脚本：数据源是什么？输出格式是什么？运行频率？
- 微服务架构：服务间通信方式（gRPC/REST/消息队列）？是否使用服务网格？分布式追踪方案？
- Monorepo：使用什么包管理工具（pnpm/turbo/nx）？哪些包需要独立发布？
- 库/SDK：目标运行环境（浏览器/Node.js/多端）？打包格式（ESM/CJS/UMD）？
- CLI 工具：目标平台（跨平台/仅 Linux）？是否需要全局安装？插件机制？

### 步骤 4：识别约束与风险

在收集信息的过程中，主动识别潜在的约束和风险：

- **技术约束**：必须使用特定框架、特定数据库、特定部署环境
- **合规约束**：涉及用户数据、支付、个人信息保护
- **性能约束**：高并发、大数据量、低延迟要求
- **兼容性约束**：需要支持旧浏览器、特定操作系统版本
- **集成约束**：需要对接第三方系统、API、SDK
- **合规约束**：涉及 GDPR、数据安全法、个人信息保护法等法规要求
- **多租户约束**：需要支持多租户隔离、数据权限分级
- **高可用约束**：需要 99.9%+ 可用性、容灾备份、故障自动转移

将识别到的约束和风险记录到需求摘要中。

### 步骤 5：整理需求摘要

将所有收集到的信息整理为结构化需求摘要。

## 三、输出格式

### 需求摘要模板

```markdown
# 需求摘要

## 基本信息
- 项目名称：[项目名称]
- 项目类型：[Web网站 / Web应用 / API服务 / 小程序 / 数据脚本 / 其他]
- 提出人：[用户名称]
- 提出时间：[YYYY-MM-DD HH:MM]

## 原始需求
> [用户原始描述，原文记录]

## 项目目标
[1-3 句话描述项目要解决的核心问题和预期价值]

## 目标用户
- 主要用户：[描述]
- 次要用户：[描述，如无则省略]

## 核心功能列表
| 序号 | 功能名称 | 优先级 | 描述 |
|------|---------|--------|------|
| 1    | [功能名] | P0(必须) | [简要描述] |
| 2    | [功能名] | P1(重要) | [简要描述] |
| 3    | [功能名] | P2(可选) | [简要描述] |

## 技术约束
- 技术栈：[已确定的，或"待定"]
- 部署环境：[Docker / K8s / 传统服务器 / 待定]
- 兼容性：[浏览器/系统/设备要求]
- 其他约束：[如有]

## 参考案例
- [案例名称]：[参考链接或描述]

## 风险与注意事项
- [风险1]：[描述及建议]

## 时间要求
- 期望交付时间：[日期或"待定"]
- 硬性截止日期：[日期或"无"]
```

### HITL G1 门控卡片

需求摘要整理完成后，向用户发送 G1 门控审核卡片：

```
[G1] 需求确认 - [项目名称]

项目类型：[类型]
核心功能：
1. [功能1]
2. [功能2]
3. [功能3]

技术方案：[简要说明]
时间要求：[说明]

[确认，继续] [需要补充]
```

## 四、输出标准

- 需求摘要不超过 800 字（详细功能描述留到 PRD 阶段）
- 必须包含：项目类型、核心功能列表、技术约束
- 原始需求原文保留，不做改写
- 所有不确定的信息标记为「待定」而非自行假设
- G1 门控卡片必须附带「确认」和「需要补充」两个选项

## 五、门控流转

| 用户操作 | 流转方向 |
|---------|---------|
| 点击「确认，继续」 | 进入 PRD 阶段（prd 技能） |
| 点击「需要补充」 | 根据用户补充信息重新整理需求摘要，再次发送 G1 卡片 |
| 超时未响应（24h） | 发送提醒，48h 未响应则暂停任务 |
