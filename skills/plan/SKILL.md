## 一、技能概述

计划拆解阶段将 PRD 中的功能需求转化为具体的、可执行的开发任务。每个任务应当足够小，能够独立完成、独立测试、独立提交。

**核心原则：**
- 原子性：每个任务只做一件事，可独立验证
- 有序性：任务之间有明确的依赖关系和执行顺序
- 可估算：每个任务有明确的时间预估
- 可追溯：每个任务都能对应到 PRD 中的功能需求

## 二、执行步骤

### 步骤 1：阅读 PRD 文档

获取 G2 门控通过的 PRD 文档，重点关注：
- 功能需求列表及优先级
- 技术选型
- 页面/接口设计
- 验收标准
- 时间估算

### 步骤 2：拆解为开发任务

将每个功能需求拆解为 1-N 个开发任务。拆解粒度标准：

- 单个任务预估时间不超过 30 分钟
- 单个任务产出可独立运行/验证
- 单个任务涉及文件不超过 5 个

**按项目类型的拆解模板：**

#### Web 网站项目

```
1. 初始化项目脚手架（框架 + 目录结构 + 依赖安装）
2. 配置构建工具（Vite/Webpack + 开发服务器）
3. 搭建页面路由和公共布局（导航栏 + 页脚）
4. 开发 [页面A] 组件和样式
5. 开发 [页面B] 组件和样式
6. 响应式适配（移动端/平板/桌面）
7. SEO 优化（meta 标签 + 语义化 HTML）
8. 性能优化（图片懒加载 + 代码分割）
```

#### Web 应用项目

```
1. 初始化项目脚手架（前端 + 后端）
2. 设计数据库表结构并创建迁移脚本
3. 搭建后端 API 框架（路由 + 中间件 + 错误处理）
4. 实现用户认证模块（注册/登录/JWT）
5. 实现权限控制中间件
6. 开发 [模块A] CRUD API
7. 开发 [模块A] 前端页面
8. 开发 [模块B] CRUD API
9. 开发 [模块B] 前端页面
10. 前后端联调
11. 配置 Docker 容器化
```

#### API 服务项目

```
1. 初始化项目脚手架（框架 + 目录结构）
2. 配置数据库连接和 ORM
3. 搭建中间件链（日志/鉴权/CORS/错误处理）
4. 定义数据模型和迁移脚本
5. 实现 [资源A] API（CRUD + 校验）
6. 实现 [资源B] API（CRUD + 校验）
7. 编写 API 文档（OpenAPI/Swagger）
8. 编写单元测试
9. 配置 Docker 容器化
```

#### 数据脚本项目

```
1. 初始化项目脚手架（Python + 虚拟环境）
2. 编写数据源连接模块
3. 编写数据清洗/转换逻辑
4. 编写输出模块（CSV/Excel/DB）
5. 编写主流程编排
6. 添加日志和错误处理
7. 编写配置文件模板
8. 编写使用说明
```

#### 微服务架构项目

```
1. 初始化 Monorepo 仓库（pnpm workspace / turbo / nx）
2. 搭建 API 网关（路由转发 / 认证鉴权 / 限流熔断）
3. 搭建服务注册与发现（Consul / Nacos / K8s Service）
4. 配置分布式链路追踪（Jaeger / SkyWalking）
5. 实现用户服务（认证 / 授权 / 用户管理）
6. 实现 [业务服务A]（独立数据库 / 独立部署）
7. 实现 [业务服务B]（独立数据库 / 独立部署）
8. 配置消息队列（Kafka / RabbitMQ）处理异步事件
9. 实现服务间通信（gRPC / REST / 消息队列）
10. 配置集中式配置管理（Apollo / Nacos / ConfigMap）
11. 编写服务间集成测试
12. 配置 Docker Compose / K8s 编排文件
```

#### 库 / SDK 项目

```
1. 初始化项目脚手架（TypeScript / Rust / Go）
2. 配置构建工具（tsup / rollup / cargo / esbuild）
3. 定义公共类型和接口
4. 实现核心功能模块
5. 编写单元测试（覆盖率 ≥ 90%）
6. 配置文档生成工具（TypeDoc / rustdoc / godoc）
7. 编写使用示例和快速上手指南
8. 配置 CI/CD 自动发布流程（semantic-release / changesets）
9. 编写 CHANGELOG.md
```

### 步骤 3：确定执行顺序

按依赖关系排列任务：

1. **基础设施类**（先做）：项目初始化、目录结构、依赖安装
2. **数据层**（次之）：数据库设计、模型定义、迁移脚本
3. **核心逻辑**（再次）：API 实现、业务逻辑、核心组件
4. **界面层**（随后）：页面开发、组件实现
5. **集成层**（最后）：联调、优化、文档

标注每个任务的前置依赖：

```
任务 3 依赖：任务 1, 任务 2
任务 5 依赖：任务 3
```

### 步骤 4：分配模型

根据任务复杂度选择合适的 AI 模型：

| 复杂度 | 任务类型 | 推荐模型层级 | 预估费用/次 |
|-------|---------|------------|------------|
| 简单 | 初始化脚手架、配置文件、简单 CRUD | 低成本模型（Flash/Mini 系列） | 0.01-0.05 元 |
| 中等 | 页面开发、组件实现、业务逻辑 | 标准模型（Pro/Plus 系列） | 0.1-0.5 元 |
| 复杂 | 架构设计、复杂算法、系统集成 | 高质量模型（Max/Opus 系列） | 1-5 元 |

**模型选择原则：**
- 日常编码任务用低成本模型
- 复杂逻辑和架构设计用高质量模型
- 预算敏感时全部使用低成本模型

### 步骤 5：风险评估

对计划进行风险评估：

- **技术风险**：使用了不熟悉的技术栈、依赖不稳定的三方库
- **依赖风险**：依赖外部 API 或服务可能不可用
- **时间风险**：任务预估时间可能偏差较大
- **集成风险**：多个模块联调时可能出问题
- **合规风险**：涉及用户数据处理、支付、个人信息收集可能违反法规
- **数据迁移风险**：从旧系统迁移数据可能丢失或损坏
- **回滚风险**：部署失败后无法快速回滚到稳定版本

为每个高风险点制定应对策略。

### 步骤 6：输出开发计划

## 三、输出格式

### 开发计划模板

```markdown
# 开发计划

## 项目信息
- 项目名称：[名称]
- 技术栈：[前端 / 后端 / 数据库]
- 总预估时间：[X] 分钟

## 任务列表

| 序号 | 任务描述 | 类型 | 前置依赖 | 预估时间 | 模型 |
|------|---------|------|---------|---------|------|
| 1    | 初始化项目脚手架 | 基础 | - | 3 min | GLM-4 |
| 2    | 搭建路由和布局 | 基础 | 1 | 5 min | GLM-4 |
| 3    | 开发首页 | 开发 | 2 | 8 min | Claude |
| 4    | 响应式适配 | 优化 | 3 | 5 min | GLM-4 |
| 5    | 测试与优化 | 测试 | 4 | 5 min | Claude |

## 执行顺序

1 -> 2 -> 3 -> 4 -> 5

## 风险评估

| 风险项 | 等级 | 应对策略 |
|-------|------|---------|
| [风险1] | 中 | [策略] |
```

### HITL G3 门控卡片

```
[G3] 计划审查 - [项目名称]

开发计划（共 [N] 个任务）：
序号 | 任务描述        | 预估时间 | 模型
-----|----------------|---------|------
1    | 初始化项目       | 3 min   | GLM-4
2    | 搭建路由布局     | 5 min   | GLM-4
3    | 开发首页         | 8 min   | Claude
...

总预估时间：约 [X] 分钟
技术栈：[前端 / 后端 / 数据库]

[批准执行] [调整计划]
```

## 四、输出标准

- 每个任务描述清晰、可执行，不超过 1 句话
- 任务之间有明确的先后顺序和依赖关系
- 标注每个任务的预估时间和使用的模型
- 单个任务预估时间不超过 30 分钟
- 开发计划保存为 `workspace/[项目名]/docs/PLAN.md`
- G3 门控卡片以表格形式展示任务列表

## 五、门控流转

| 用户操作 | 流转方向 |
|---------|---------|
| 点击「批准执行」 | 进入开发执行阶段（dev 技能），AI 全自动开发 |
| 点击「调整计划」 | 根据用户反馈调整计划，重新发送 G3 卡片 |
| 超时未响应（24h） | 发送提醒，48h 未响应则暂停任务 |

**重要：** G3 门控通过后，AI 将自动完成所有开发工作（Dev + Test），直到开发完成才会再次通知用户（进入 G4 部署验收）。
