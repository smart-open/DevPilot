## 一、技能概述

需求分析阶段将 Explore 阶段的粗粒度需求摘要转化为完整的产品需求文档（PRD）。PRD 是开发团队的「施工图纸」，必须清晰、完整、可执行。

**核心原则：**
- 完整性：覆盖功能需求、非功能需求、验收标准
- 可执行性：开发人员能直接根据 PRD 开始编码
- 可验证性：每个需求都有明确的验收标准
- 无歧义：用词精确，避免「大概」「可能」「尽量」等模糊表述

## 二、执行步骤

### 步骤 1：阅读需求摘要

获取 Explore 阶段产出的需求摘要，理解：
- 项目类型和目标
- 核心功能列表及优先级
- 技术约束和风险
- 时间要求

### 步骤 2：编写 PRD 文档

按以下章节结构编写完整的 PRD 文档。

#### 第一章：项目概述

- **项目背景**：为什么要做这个项目？解决什么业务痛点？
- **项目目标**：可量化的目标（如「支持 1000 并发用户」「页面加载 < 2s」）
- **目标用户画像**：主要用户群体的特征、使用场景、技术水平
- **项目范围**：明确什么在范围内、什么不在范围内（防止范围蔓延）

#### 第二章：功能需求

每个功能需求按以下格式描述：

```markdown
### 功能 [编号]：[功能名称]

**优先级**：P0(必须) / P1(重要) / P2(可选)
**描述**：[一段话描述功能要做什么]
**用户故事**：
  作为 [角色]，我希望 [功能]，以便 [价值]
**输入**：[用户需要提供什么]
**输出**：[系统返回什么]
**业务规则**：
  1. [规则1]
  2. [规则2]
**异常处理**：
  - [异常场景1]：[处理方式]
  - [异常场景2]：[处理方式]
```

#### 第三章：页面设计 / 接口设计

**Web/小程序项目 - 页面设计：**

| 页面 | 路由 | 核心元素 | 交互说明 |
|------|------|---------|---------|
| 首页 | / | 导航栏、轮播图、产品卡片 | 点击卡片跳转详情页 |
| 详情页 | /detail/:id | 商品图片、描述、购买按钮 | 点击购买进入结算 |

**API 服务项目 - 接口设计：**

| 接口 | 方法 | 路径 | 请求参数 | 响应格式 |
|------|------|------|---------|---------|
| 获取列表 | GET | /api/items | page, size | { code, data, total } |
| 创建 | POST | /api/items | name, desc | { code, data } |
| 更新 | PUT | /api/items/:id | name, desc | { code, data } |
| 删除 | DELETE | /api/items/:id | - | { code } |

#### 第三章补充：数据模型设计

对于涉及数据库的项目，提供数据模型设计：

```markdown
### 数据模型

#### 实体关系图（ER Diagram）

[用文字描述实体间的关系，或附上 ER 图]

#### 表结构设计

| 表名 | 字段名 | 类型 | 约束 | 说明 |
|------|--------|------|------|------|
| users | id | BIGINT | PK, AUTO | 主键 |
| users | username | VARCHAR(64) | UNIQUE, NOT NULL | 用户名 |
| users | email | VARCHAR(128) | UNIQUE, NOT NULL | 邮箱 |
| users | created_at | TIMESTAMP | DEFAULT NOW | 创建时间 |

#### 索引设计

| 表名 | 索引名 | 字段 | 类型 | 说明 |
|------|--------|------|------|------|
| users | idx_user_email | email | UNIQUE | 邮箱唯一索引 |
| users | idx_user_created | created_at | BTREE | 按创建时间查询 |
```

#### 第三章补充：API 契约设计

对于 API 服务项目，提供详细的 API 契约：

```markdown
### API 契约

#### 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "timestamp": 1234567890
}
```

#### 错误码定义

| 错误码 | HTTP 状态码 | 说明 |
|--------|-----------|------|
| 0 | 200 | 成功 |
| 1001 | 400 | 参数校验失败 |
| 1002 | 401 | 未认证 |
| 1003 | 403 | 无权限 |
| 1004 | 404 | 资源不存在 |
| 2001 | 500 | 服务内部错误 |
```

#### 第四章：技术选型

根据项目类型和约束，推荐技术栈：

| 项目类型 | 推荐前端 | 推荐后端 | 推荐数据库 | 推荐部署 |
|---------|---------|---------|-----------|---------|
| Web 网站 | React/Vue + TailwindCSS | 无 / Node.js Express | 无 / SQLite | Nginx 静态托管 |
| Web 应用 | React + Ant Design | Node.js(NestJS) / Python(FastAPI) | PostgreSQL/MySQL | Docker Compose |
| API 服务 | 无 | Go(Gin) / Java(Spring Boot) / Python(FastAPI) | PostgreSQL/Redis | Docker / K8s |
| 小程序 | 原生/Uni-app | Node.js / Java | MySQL | 云服务器 |
| 数据脚本 | 无 | Python | CSV/Excel/DB | Cron / Airflow |
| 微服务 | - | Go(Go-Zero) / Java(Spring Cloud) / Node(NestJS) | PostgreSQL + Redis + Kafka | K8s + Istio |
| 库/SDK | - | TypeScript / Rust / Go | - | npm / PyPI / Crates.io |
| CLI 工具 | - | Go(Cobra) / TypeScript(Commander) / Rust(Clac) | - | Homebrew / npm |
| 桌面应用 | Electron / Tauri | - | SQLite | electron-builder / tauri build |

说明选择理由，列出备选方案。

#### 第五章：非功能需求

- **性能需求**：响应时间、并发数、吞吐量
- **安全需求**：认证方式、授权策略、数据加密、输入校验
- **可用性需求**：SLA 目标、故障恢复时间
- **兼容性需求**：浏览器版本、操作系统、设备类型
- **可维护性需求**：代码规范、文档要求、日志规范
- **可扩展性需求**：预留扩展点、模块化设计
- **合规性需求**：数据保护法规遵循（GDPR / 数据安全法 / 个保法）、行业认证要求（等保 / PCI-DSS / HIPAA）
- **可观测性需求**：日志收集、指标监控（Prometheus）、链路追踪（Jaeger / SkyWalking）、告警策略
- **多租户需求**（如适用）：数据隔离级别（数据库级 / 行级）、租户资源配额、自定义配置

#### 第六章：验收标准

每个功能需求对应的验收标准，使用 Given-When-Then 格式：

```markdown
### 验收标准 [对应功能编号]

**场景 1：[正常流程]**
- Given [前置条件]
- When [用户操作]
- Then [预期结果]

**场景 2：[异常流程]**
- Given [前置条件]
- When [异常操作]
- Then [错误处理结果]
```

#### 第七章：时间估算

| 阶段 | 任务 | 预估时间 | 使用的模型 |
|------|------|---------|-----------|
| 开发 | [任务1] | [X min] | [模型名] |
| 开发 | [任务2] | [X min] | [模型名] |
| 测试 | 单元测试 | [X min] | - |
| 测试 | 集成测试 | [X min] | - |
| 部署 | 构建部署 | [X min] | - |
| **合计** | | **[X min]** | |

### 步骤 3：保存 PRD 文档

将 PRD 文档保存为 Markdown 文件：

```
workspace/[项目名]/docs/PRD.md
```

### 步骤 4：发送 G2 门控卡片

## 三、HITL G2 门控卡片

```
[G2] PRD 审核 - [项目名称]

需求文档已完成，共 7 章节：
一、项目概述（背景、目标、用户画像）
二、功能需求（[N] 个功能点）
三、页面/接口设计（[N] 个页面/接口）
四、技术选型（[技术栈]）
五、非功能需求（性能、安全、兼容性）
六、验收标准（[N] 条）
七、时间估算（约 [X] 分钟）

预估工期：[X-Y] 小时
详细文档：[查看完整PRD]

[审核通过] [需要修改]
```

## 四、输出标准

- PRD 文档保存为 Markdown 文件，存放在 `workspace/[项目名]/docs/PRD.md`
- 每个功能需求必须有用户故事和验收标准
- 技术选型必须有选择理由
- 时间估算精确到分钟级别
- 非功能需求不遗漏（至少覆盖性能、安全、兼容性）
- G2 门控卡片摘要不超过 1000 字

## 五、门控流转

| 用户操作 | 流转方向 |
|---------|---------|
| 点击「审核通过」 | 进入计划拆解阶段（plan 技能） |
| 点击「需要修改」 | 根据用户反馈修改 PRD，重新发送 G2 卡片 |
| 超时未响应（24h） | 发送提醒，48h 未响应则暂停任务 |
